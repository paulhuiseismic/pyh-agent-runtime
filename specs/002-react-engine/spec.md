# Feature Specification: ReAct 引擎

**Feature Branch**: `002-react-engine`

**Created**: 2026-07-25

**Status**: Draft

**Input**: User description: "ReAct 引擎：实现内核 react 模块的完整 ReAct 循环，替换 001 中的
SingleShotReactLoop 占位实现。循环在'思考-行动-观察'步骤间迭代：每步可决定调用 provider
完成一次 LLM 推理，或调用 tool 模块的已注册工具，直到得出最终答案或达到调用方指定的
max_steps 上限。max_steps 必须由调用方显式提供且为正整数，达到上限时循环必须终止并返回
明确的失败结果。循环的每一步都通过 provider 发起 LLM 调用，因此自动继承 provider 已有的
超时、token/成本上限与 OTel span；循环本身也需要发出标识当前步数、调用工具的 span 属性。
工具调用通过 tool 模块的 Tool Protocol 进行，工具执行失败必须被循环捕获为一次观察结果
反馈给下一轮思考。循环不依赖任何平台层组件，可独立单元测试。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 通过多轮思考与工具调用得出最终答案 (Priority: P1)

作为内核的上层调用方，我提交一个目标（goal）与可用工具集合，ReAct 引擎在
思考-行动-观察的循环中反复推理：每步决定是直接回答，还是调用某个已注册工具
获取更多信息，直至得出最终答案并返回。

**Why this priority**: 这是 ReAct 引擎存在的全部意义——没有多步推理与工具调用的
编排能力，引擎退化为 001 中的占位实现，无法构成"可用工具解决复杂目标"的核心价值。

**Independent Test**: 用 stub provider（按预设脚本返回"调用工具"或"给出最终答案"的
LLM 响应）与 stub tool（返回固定观察结果）驱动一次完整运行，验证最终答案与循环步数
符合预期，全程不需要真实模型或平台层组件。

**Acceptance Scenarios**:

1. **Given** 一个目标和一个可用工具, **When** 引擎运行, **Then** 引擎先决定调用工具、
   将工具的观察结果反馈给下一轮思考，最终在工具结果基础上给出答案。
2. **Given** 一个目标不需要任何工具即可回答, **When** 引擎运行,
   **Then** 引擎在第一步即给出最终答案，不发起工具调用。
3. **Given** 引擎决定调用一个未注册的工具, **When** 该步执行,
   **Then** 该步作为一次失败的观察结果反馈给下一轮思考（而非终止整个循环）。

---

### User Story 2 - 达到最大步数时明确终止 (Priority: P2)

作为调用方，当目标未能在我设定的步数上限内解决时，引擎必须在达到上限的那一步
终止并返回类型明确的失败结果（说明已执行的步数与最后一次观察），而不是抛出
未分类异常、无限循环或悄悄返回一个不完整的答案。

**Why this priority**: 这是宪法强制要求（原则 VI：ReAct 循环必须有最大步数限制）；
多租户环境中，无界循环等同于无界成本与延迟，必须与循环能力同期交付。

**Independent Test**: 用一个"永远决定调用工具、从不给出最终答案"的 stub provider
驱动运行，设置 max_steps=3，验证引擎恰好执行 3 步后终止并返回类型化的
"步数耗尽"结果，不抛未分类异常。

**Acceptance Scenarios**:

1. **Given** max_steps 设为一个正整数 N, **When** 引擎在 N 步内未得出最终答案,
   **Then** 引擎在第 N 步后终止，返回"步数耗尽"类型的失败结果，
   包含已执行步数与最后一次观察内容。
2. **Given** 调用方未提供 max_steps 或提供非正整数, **When** 发起运行,
   **Then** 请求在开始任何步骤之前被拒绝，返回明确的参数错误。
3. **Given** max_steps=1, **When** 第一步引擎即决定调用工具而非给出答案,
   **Then** 引擎在该步后立即终止并返回"步数耗尽"结果（不额外多跑一步）。

---

### User Story 3 - 每次运行可按步骤与工具追溯 (Priority: P3)

作为运维/审计人员，一次完整的 ReAct 运行会产生可追溯的遥测记录：
除每个内部 LLM 调用自带的 span（继承自 provider，含 tenant_id）外，
引擎自身也标注当前是第几步、该步是否调用了工具及调用了哪个工具，
使我可以还原一次运行的完整决策路径。

**Why this priority**: 可观测性是宪法强制要求（原则 V）；但它是对已有调用能力的
增强而非阻塞项，故列为 P3。

**Independent Test**: 用内存型遥测采集器运行一次含 2 次工具调用的多步场景，
验证产生的 span 集合包含每步的步数标注与工具调用标注，且都可与该运行的
上层标识关联。

**Acceptance Scenarios**:

1. **Given** 一次多步运行, **When** 运行完成, **Then** 每一步产生的 span 均标注
   当前步数（从 1 开始）；调用了工具的步还标注工具名。
2. **Given** 一次因步数耗尽而终止的运行, **When** 运行终止,
   **Then** 遥测记录同样完整，可识别出该运行是"步数耗尽"而非正常完成。
3. **Given** 遥测后端不可用, **When** 引擎运行, **Then** 运行本身正常完成，
   遥测缺失不影响最终答案或失败结果。

---

### Edge Cases

- 工具执行抛出异常（而非返回业务失败）时，该异常被引擎捕获为一次失败的观察结果，
  循环继续到下一步，不中断整个运行。
- provider 调用本身失败（超时/超限/连接失败等，均为 001 已定义的类型化异常）时，
  整个 ReAct 运行以该异常类型终止并原样上抛——推理失败不同于步数耗尽，
  调用方需要能区分两者。
- 同一个目标被并发运行多次（不同 tenant_id）时，各运行的步数计数、
  遥测标注互不串扰。
- goal 为空字符串时，请求在开始任何步骤之前被拒绝。
- 引擎在同一步内决定调用工具但未提供工具所需参数（工具侧校验失败）时，
  按边界规则处理为一次失败的观察结果，不是引擎层错误。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 引擎 MUST 提供统一的运行入口：接收目标（goal）、租户标识（tenant_id）、
  最大步数（max_steps）、可用工具集合，返回最终答案或类型化的失败结果。
- **FR-002**: max_steps MUST 由调用方显式提供且为正整数；缺失或非正整数 MUST 在
  开始任何步骤之前被拒绝，返回明确的参数错误（继承 001 已有的校验错误类型）。
- **FR-003**: 引擎 MUST 在"思考"步骤中通过 provider 发起一次 LLM 调用，
  由该次调用的结果决定"给出最终答案"或"调用某个工具"两种行动之一。
- **FR-004**: 当决定的行动是调用工具时，引擎 MUST 通过 tool 模块的 Tool Protocol
  执行该工具，并将执行结果（成功内容或失败信息）作为"观察"反馈给下一轮思考。
- **FR-005**: 工具执行失败（工具未注册、工具抛异常、工具返回错误）MUST 被引擎捕获
  为一次失败的观察结果并继续循环，MUST NOT 导致整个运行崩溃。
- **FR-006**: 引擎 MUST 在每次到达 max_steps 而仍未得出最终答案时终止运行，
  返回"步数耗尽"类型的失败结果，包含已执行步数与最后一次观察内容；
  MUST NOT 超出 max_steps 继续执行。
- **FR-007**: provider 调用本身产生的类型化异常（超时/token 超限/成本超限/
  连接失败/响应格式错误/参数错误）MUST 原样中断当前运行并上抛给调用方，
  MUST NOT 被引擎当作"失败的观察结果"吞掉重试。
- **FR-008**: 引擎的每一步 MUST 产生可关联到该次运行的遥测标注：当前步数（从 1
  开始）、本步是否调用工具、调用的工具名（若有）；MUST 与 provider 自带的
  span（含 tenant_id）共同构成完整的运行轨迹。
- **FR-009**: 遥测发送失败 MUST NOT 影响运行本身的执行与结果（延续 001 的遥测容错要求）。
- **FR-010**: react 模块 MUST NOT 依赖任何平台层组件；引擎的单元测试 MUST 使用
  stub provider 与 stub tool 驱动，MUST NOT 依赖真实模型服务或真实工具执行环境。
- **FR-011**: 引擎实现 MUST 替换 001 中的 `SingleShotReactLoop` 占位实现，
  但 MUST NOT 改变 001 已冻结的 `ReactLoop` Protocol 签名
  （`run(goal, *, tenant_id, max_steps) -> str`）。

### Key Entities

- **运行请求**: 一次 ReAct 运行的输入——goal、tenant_id、max_steps、可用工具集合
  （工具名到 Tool 实例的映射）。
- **步骤记录**: 单步的内部状态——步数序号、本步的思考结果（最终答案或行动决策）、
  若调用工具则含工具名与观察结果。
- **观察结果**: 一步行动执行后反馈给下一轮思考的内容——可以是工具的成功输出，
  也可以是工具失败的说明（未注册、异常、业务失败）。
- **运行结果**: 成功时为最终答案字符串；步数耗尽时为类型化的失败结果
  （含已执行步数与最后一次观察）；provider 异常时原样上抛。
- **运行遥测轨迹**: 一次运行产生的全部 span 集合——每步的步数/工具标注 +
  该步内 provider 调用自带的 GenAI span。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在无平台层组件、无真实模型、无真实工具执行环境的条件下，
  react 模块全部单元测试可一次性通过。
- **SC-002**: 100% 达到 max_steps 上限的运行返回类型化的"步数耗尽"结果，
  且引擎实际执行的步数不超过 max_steps。
- **SC-003**: 100% 的工具执行失败（未注册/异常/业务失败）被转化为观察结果反馈给
  下一轮思考，不导致运行以未分类异常终止。
- **SC-004**: 抽查任意一次多步运行的遥测记录，可还原出每一步的步数与
  是否调用了工具、调用了哪个工具。
- **SC-005**: 新开发者按后续 plan 阶段产出的验证指南，可在 15 分钟内用 stub
  跑通一次含工具调用与一次步数耗尽的完整场景。

## Assumptions

- 引擎与 LLM 之间"思考结果是最终答案还是工具调用决策"的具体交换格式
  （如结构化输出或特定文本约定）留待 plan 阶段确定技术实现，本 spec 只约束
  行为契约：每步产生"最终答案"或"工具调用"二选一的决策。
- 一次运行只能同时决定调用一个工具（不支持单步并行调用多个工具）；
  并行工具调用作为未来可能的增强，不在本 feature 范围。
- 引擎不做任何重试：单步的 provider 异常直接中断运行；单步的工具失败计入
  一次观察结果消耗一个步数，不额外重试同一步。
- 工具集合由调用方在每次运行时传入，工具的注册与生命周期管理不在本 feature
  范围（那是更上层——可能是平台层或未来的 tool 模块增强——的职责）。
- 安全默认值（如引擎自身对每步"思考"阶段的隔离超时）沿用 provider 在 001 中
  已有的超时/成本/token 上限机制，不在 react 层重复定义新的限额概念。
