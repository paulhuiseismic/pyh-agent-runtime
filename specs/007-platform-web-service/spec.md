# Feature Specification: 平台服务层 + web service（REST API）

**Feature Branch**: `007-platform-web-service`

**Created**: 2026-08-01

**Status**: Draft

**Input**: User description: "007-platform-web-service: 平台服务层 + web service（REST API）——为已完成的五大内核能力（provider/react/memory 会话记忆与长期记忆/tool+沙箱+MCP）提供统一的对外 REST API 调用入口，负责请求路由、租户识别、运行调度（并发控制）、以及内核调用结果的返回；作为后续 CLI 入口（008）复用的同一平台服务层，是内核与外部世界之间的第一个平台层薄适配。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 通过 REST API 发起一次 agent 调用并获得结果 (Priority: P1)

作为该 runtime 的外部调用方，我通过一个 REST 接口提交一次调用请求（说明我所属的
租户、要完成的目标/问题，以及可选的会话标识），无需了解背后由 provider、
ReAct 循环、memory、tool 等哪些内核能力组合完成，即可获得最终结果。

**Why this priority**: 这是本 feature 的核心价值——把已经完成的五大内核能力
第一次对外暴露为可被外部系统调用的服务，没有这一步，内核能力只能在进程内被
直接调用，无法成为真正的"平台"。

**Independent Test**: 可通过启动服务、用一个真实 HTTP 请求（携带租户标识与
问题）独立验证：请求被正确路由到内核、内核完成一次 ReAct 调用、响应中包含
最终结果。

**Acceptance Scenarios**:

1. **Given** 服务已启动且已配置至少一个可用租户，**When** 携带合法租户标识
   和一个具体问题发起请求，**Then** 响应中包含该问题对应的最终结果与
   成功状态。
2. **Given** 一次请求正在处理，**When** 请求处理过程中内核任一环节（如 LLM
   调用）失败，**Then** 响应中包含明确的失败状态与可读的失败原因，而不是
   无响应或不可分类的错误。
3. **Given** 一个已存在的会话标识，**When** 携带该会话标识发起新请求，
   **Then** 该请求复用此前会话已经积累的上下文（会话记忆，003）。

---

### User Story 2 - 运行调度与并发控制保护共享资源 (Priority: P2)

作为该平台的运维方，我需要对"同时有多少个调用请求在被处理"设置上限
（针对单个租户与针对整个平台两个维度），避免任何一个租户的高频调用拖垮
其他租户的服务质量，或让内核资源被无限制占用。

**Why this priority**: 这是多租户 runtime 的基本可用性保障，但依赖 P1
已经建立的请求处理路径才能实施限流判断，因此排在其后。

**Independent Test**: 可通过配置一个很小的并发上限，并发发起超过上限数量的
请求，独立验证：超出上限的请求得到明确的"超过限制"响应，未超出上限的请求
正常完成，且不影响其他租户的请求处理。

**Acceptance Scenarios**:

1. **Given** 某租户的并发调用数已达到其配置上限，**When** 该租户再次发起
   新请求，**Then** 该请求得到明确的"超过并发上限"响应，而不是被无限期挂起。
2. **Given** 平台整体并发调用数已达到全局上限，**When** 任意租户发起新请求，
   **Then** 该请求同样得到明确的"超过并发上限"响应。
3. **Given** 租户 A 的请求已达到其并发上限，**When** 租户 B 发起新请求且
   未超过租户 B 自身与全局上限，**Then** 租户 B 的请求正常被处理，不受
   租户 A 状态影响。

---

### User Story 3 - 请求被正确识别租户并与内核遥测打通 (Priority: P3)

作为该平台的运维/合规方，我需要每一个进入平台的请求都被准确识别所属租户，
并且这个租户标识一路传递到内核发出的每一次 LLM 调用、工具执行的可观测记录
中，以便按租户核算成本、定位问题。

**Why this priority**: 这是合规与可观测性的基础要求，但技术上依赖 P1 已经
建立的请求路由路径，只是在其上补充"租户标识必须贯穿"这一约束，因此排在
调度控制（P2）之后作为独立可验证的收尾能力。

**Independent Test**: 可通过发起一次请求后检查该请求触发的全部内核可观测
记录（span），独立验证每条记录都携带与请求一致的租户标识；同时验证未携带
合法租户标识的请求在到达任何内核能力之前就被拒绝。

**Acceptance Scenarios**:

1. **Given** 一个未携带任何租户标识的请求，**When** 提交该请求，**Then**
   请求在触发任何内核调用之前即被拒绝，返回明确的"身份识别失败"响应。
2. **Given** 一个携带合法租户标识的请求，**When** 该请求触发内核的 LLM
   调用、工具调用等操作，**Then** 这些操作产生的全部可观测记录都携带与
   该请求一致的租户标识。

---

### Edge Cases

- provider（模型路由）配置缺失或无效（如未配置可达的模型服务地址、
  或请求的模型未配置成本单价）时，系统 MUST 在启动阶段即拒绝启动，
  不接受任何请求——这是平台级别的全局配置，不存在"某个租户未配置"的
  情形（架构决策：`model`/provider 连接信息为平台级配置而非按租户配置，
  见 data-model.md FR-013/FR-014）。
- 单次调用触发的内核处理耗时超出平台自身能接受的等待上限时，如何响应
  （对应宪法原则 IV 的"外部调用超时"精神，延伸到平台自身的请求生命周期，
  见 FR-009）？
- 同一租户在同一会话标识下发起并发请求时，系统 MUST 对同一
  `session_id` 的处理进行串行化，避免交叉写入导致会话历史顺序错乱或
  更新丢失（见 FR-015）。
- 请求体格式错误（缺少必填字段、字段类型错误）时，如何与"租户身份识别失败"
  "内核调用失败"区分开（见 FR-007）？

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 提供一个网络可访问的接口，接收「租户标识 + 目标/
  问题描述 + 可选会话标识」，并返回内核处理后的最终结果，调用方无需了解
  内部由哪些内核能力（provider/react/memory/tool）组合完成。
- **FR-002**: 系统 MUST 对每一个进入平台的请求识别其所属租户；无法识别出
  合法租户的请求 MUST 在触发任何内核调用之前被拒绝。
- **FR-003**: 系统 MUST 将请求路由到内部统一的处理路径（内核能力的组合
  调用），该路径 MUST NOT 与对外暴露的接口形式（REST）耦合，以便未来
  CLI 入口（008）复用同一处理路径而不重复实现路由/租户识别/调度逻辑。
- **FR-004**: 系统 MUST 支持为每个租户配置一个最大并发处理请求数上限；
  超过该上限的新请求 MUST 得到明确的"超过并发上限"响应。
- **FR-005**: 系统 MUST 支持配置一个平台级别的全局最大并发处理请求数上限；
  超过该上限的新请求（无论所属租户）MUST 得到明确的"超过并发上限"响应。
- **FR-006**: 系统 MUST 将识别出的租户标识传递给该请求触发的每一次内核调用
  （LLM 调用、工具执行等），使这些调用产生的可观测记录都携带一致的租户
  标识（呼应宪法原则 V）。
- **FR-007**: 系统 MUST 为以下情形返回可区分的响应：租户身份识别失败、
  请求参数校验失败、并发上限超出、内核处理失败（如 LLM 调用失败、
  工具执行失败）、请求整体处理超时（FR-009）。
- **FR-008**: 系统 MUST 支持调用方通过提供一个已存在的会话标识，令新请求
  复用该会话已积累的历史上下文（复用 003 的会话记忆能力）；未提供会话
  标识时 MUST 视为一次全新的、无历史上下文的调用。
- **FR-009**: 系统 MUST 对每一次请求的整体处理设置一个显式的最长等待时间；
  超过该时间 MUST 终止处理并返回明确的超时响应，不允许无限期等待
  （呼应宪法原则 IV，延伸到平台自身的请求生命周期，而不仅是内核内部的
  外部调用）。

- **FR-010**: 系统 MUST 采用同步阻塞方式处理请求——调用方发起一次请求后
  等待处理完成并在同一个响应中获得最终结果，MUST NOT 提供"提交任务后轮询
  结果"的异步接口（v1 范围，用户已确认）。
- **FR-011**: 系统 MUST 通过调用方在请求中提供的静态 API Key 识别租户
  （Key 与租户一一对应，由运维预先配置好映射关系）；MUST NOT 在本 feature
  中实现用户名密码登录、OAuth2、SSO 等更复杂的身份体系（用户已确认，
  留待未来按需扩展）。
- **FR-012**: 当租户或全局并发上限被触达时，系统 MUST 立即拒绝新请求
  （返回明确的"超过并发上限"响应），MUST NOT 将请求加入队列等待资源释放
  （用户已确认，避免调用方被无限期挂起、避免引入排队机制的额外复杂度）。

*以下为 `/speckit-analyze` 发现缺口后补充的需求（C1/C2/C4 修正项）：*

- **FR-013**: 系统 MUST 支持配置访问 LLM 模型服务所需的连接信息（服务
  地址、可选凭据）；该配置缺失或无效时，系统 MUST 在启动阶段即失败，
  不接受任何请求（不存在"运行时才发现无法连接"的情形）。
- **FR-014**: 系统 MUST 支持配置每个可能被调用的模型对应的成本单价，
  用于落实宪法原则 IV 的成本上限约束；请求指定的模型若未配置单价，
  系统 MUST 拒绝该次调用（呼应 001 `PriceTable` 的既有行为，不在平台层
  重复实现，只需保证配置完整）。系统 MUST 支持（可选）配置需要接入的
  MCP server（006）列表，供启动时建立连接并注册其工具；未配置时
  `ToolRegistry` MUST 允许为空，agent 请求仍可正常处理（只是不能调用
  任何工具）。
- **FR-015**: 系统 MUST 对同一 `session_id` 的并发请求进行串行化处理
  （同一时刻只有一个请求在读取/写入该会话的历史），避免交叉写入导致
  会话历史顺序错乱或更新丢失；不同 `session_id` 之间的请求 MUST NOT
  互相阻塞。

### Key Entities *(include if feature involves data)*

- **Agent 调用请求**：一次对外请求的载荷，包含租户标识、目标/问题描述、
  可选的会话标识、可选的模型选择等调用参数。
- **Agent 调用结果**：一次请求处理完成后的返回内容，包含处理状态（成功/
  各类失败）、最终结果文本或错误详情。
- **租户身份**：请求中标识调用方所属租户的凭据（API Key）及其到租户标识
  的映射关系。
- **并发调度状态**：某一时刻"每个租户正在处理中的请求数"与"平台整体正在
  处理中的请求数"，用于判断新请求是否超出配置上限。
- **模型服务配置**：平台级别（非按租户）的模型服务连接信息、模型成本
  单价、可选的工具/MCP server 接入配置（FR-013/FR-014）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 外部调用方无需了解内核内部由哪些能力组合完成，即可通过一次
  请求获得 agent 处理结果。
- **SC-002**: 100% 未携带合法租户标识的请求，在触及任何内核资源（LLM 调用、
  工具执行等）之前即被拒绝。
- **SC-003**: 当某租户的并发请求数达到其配置上限时，该租户后续请求 100%
  在可预期的短时间内收到明确的"超过并发上限"响应，而非被无限期挂起。
- **SC-004**: 一个租户的高频调用行为（达到其并发上限）不影响其他租户
  请求的正常处理成功率。
- **SC-005**: 每一次请求触发的内核可观测记录（span），100% 携带与该请求
  一致的租户标识。
- **SC-006**: 未来新增一个非 REST 的调用入口（如 CLI）时，无需重新实现
  租户识别、请求路由与并发调度逻辑，只需复用同一套平台处理路径。
- **SC-007**: 同一会话标识下的并发请求 100% 不产生会话历史顺序错乱或
  更新丢失；不同会话标识之间的请求处理耗时不因此互相影响。

## Assumptions

- 本 feature 交付的租户身份识别机制为「静态 API Key → 租户标识」的预配置
  映射（FR-011），更完善的身份体系（登录态、令牌刷新、权限分级）留给未来
  按需迭代，不在 v1 范围。
- 请求处理为同步阻塞模型（FR-010），单次请求的最长等待时间由 FR-009 的
  显式超时约束，不提供任务提交/轮询式的异步调用体验。
- 并发上限触达时采用直接拒绝而非排队（FR-012），排队/退避重试策略留给
  未来按需评估。
- 本 feature 只覆盖"提交请求 → 获得结果"这一最小闭环；租户/API Key 的
  配置管理界面、用量审计报表等能力留给未来 feature（010 多租户强化与审计）。
- 本 feature 只对外暴露 REST 接口；CLI 入口（008）作为独立 feature 复用
  本 feature 建立的平台处理路径，不在本 feature 范围内实现。
- 模型服务连接信息、成本单价为平台级（全局）配置，不支持按租户配置不同
  的模型/服务地址（FR-013/FR-014）；v1 默认不配置任何工具/MCP server，
  `ToolRegistry` 允许为空，agent 请求在没有工具的情况下依然可以正常完成
  （仅无法调用工具）。
- 同一 `session_id` 的并发请求串行化（FR-015）采用进程内互斥（如按
  session_id 分片的锁），不追求跨进程/多实例部署下的强一致性——多实例
  场景的调度一致性留给未来按需评估（呼应 plan.md 的 Scale/Scope 边界）。
