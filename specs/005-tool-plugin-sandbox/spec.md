# Feature Specification: plugin tool 插件机制 + sandbox

**Feature Branch**: `005-tool-plugin-sandbox`

**Created**: 2026-07-26

**Status**: Draft

**Input**: User description: "plugin tool 插件机制 + sandbox：实现内核 tool 模块的完整插件注册与
沙箱执行能力，替换 001 中的 EchoTool 占位实现，不改变 001/002 已冻结的 Tool Protocol 签名。
核心能力：工具注册中心（按名称注册/查找/列出，重复名称拒绝）；沙箱执行（SandboxedTool 包装
外部命令，子进程执行，显式超时、资源限制、受限工作目录，明确声明不提供网络隔离）；失败类型化
（沙箱层面失败 vs 工具业务失败，均通过现有 Tool Protocol 机制反馈，兼容 002 ReactEngine 现有
的工具失败处理）；可观测性（每次执行产生含 tenant_id/工具名/结果类型/耗时的记录）；不依赖
平台层，可独立单元测试。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 注册与查找工具 (Priority: P1)

作为内核的上层调用方（react 模块或平台层），我可以把一个工具（无论是进程内可信实现，
还是需要隔离执行的插件）注册到工具注册中心，之后按名称查找到它，并获取当前已注册的
全部工具清单，用于构造一次 ReAct 运行所需的工具集合。

**Why this priority**: 这是插件机制的基础入口——没有统一的注册与查找能力，
"多个工具从哪里来、给谁用"就没有明确答案，后续的沙箱执行也无从谈起。

**Independent Test**: 用几个简单的示例工具（满足 Tool Protocol 的最小实现）
注册到一个新的注册中心实例，验证可按名称查到、可列出全部、重复名称注册被拒绝，
全程不需要真实的沙箱执行或平台层组件。

**Acceptance Scenarios**:

1. **Given** 一个空的工具注册中心, **When** 注册一个工具, **Then** 之后可以按该
   工具的名称查找到它，且它出现在"列出全部已注册工具"的结果中。
2. **Given** 已注册一个名为"search"的工具, **When** 尝试再注册一个同名为
   "search"的工具, **Then** 第二次注册被拒绝，原有工具保持不变。
3. **Given** 一个工具注册中心中同时注册了一个进程内可信工具和一个沙箱插件工具,
   **When** 分别按名称查找, **Then** 两者都能被正常找到，注册中心不区分二者的
   查找方式。
4. **Given** 查找一个从未注册过的工具名称, **When** 执行查找, **Then** 返回
   明确的"未找到"结果，而不是抛出未分类异常。

---

### User Story 2 - 沙箱执行一个外部命令工具 (Priority: P2)

作为调用方，当我注册的是一个"沙箱插件"类型的工具时，每次调用它的 invoke()
都会在一个隔离的子进程中执行该工具对应的外部命令，正常完成时我能拿到其标准
输出作为结果；子进程以非零退出码结束时，我能明确知道这是一次工具执行失败。

**Why this priority**: 这是沙箱能力对外的核心价值——把不受信任的第三方/租户
代码的执行结果安全地交付给调用方，但依赖 User Story 1 的注册能力才能被
统一管理，故列为第二优先级。

**Independent Test**: 用几个简单的示例脚本（正常退出、非零退出码退出）
包装为沙箱工具并调用，验证正常场景返回标准输出内容、非零退出码场景
被识别为工具执行失败，全程不需要真实的第三方插件生态。

**Acceptance Scenarios**:

1. **Given** 一个包装了"正常退出并打印结果"脚本的沙箱工具, **When** 调用
   它的 invoke(), **Then** 返回该脚本的标准输出内容。
2. **Given** 一个包装了"以非零退出码退出"脚本的沙箱工具, **When** 调用它的
   invoke(), **Then** 该次调用被识别为工具执行失败，携带足够的诊断信息
   （如退出码）。
3. **Given** 调用方向沙箱工具传入的 arguments, **When** 子进程执行,
   **Then** 该子进程能够拿到这些参数并在其输出中体现出来（验证参数正确传递）。

---

### User Story 3 - 沙箱对超时与资源超限的强制终止 (Priority: P2)

作为调用方，当沙箱工具对应的外部命令运行时间过长或消耗资源过多时，
沙箱必须在配置的上限内强制终止该子进程，并将其识别为一次沙箱层面的失败
（区别于工具自身的业务失败），而不是让调用方无限期等待或系统资源被耗尽。

**Why this priority**: 这是沙箱作为"安全边界"存在的核心保障，与 User Story 2
同等重要，但依赖沙箱执行机制已经建立（US2），故排在其后。

**Independent Test**: 用一个"故意长时间运行"的示例脚本与一个（在支持资源
限制的平台上）"故意大量占用资源"的示例脚本，验证前者在配置的超时时间内
被强制终止并识别为超时失败，后者在支持该项限制的平台上被识别为资源超限
失败。

**Acceptance Scenarios**:

1. **Given** 一个运行时间远超配置超时的沙箱工具, **When** 调用它的 invoke(),
   **Then** 该次调用在超时时间到达后被强制终止，识别为"超时"类型的失败，
   而不是无限期挂起。
2. **Given** 一个在当前运行平台上支持资源限制、且会超出配置资源上限的沙箱工具,
   **When** 调用它的 invoke(), **Then** 该次调用被识别为"资源超限"类型的失败，
   与"超时"和"非零退出码"可区分。
3. **Given** 调用方未显式配置超时或资源上限, **When** 构造一个沙箱工具,
   **Then** 采用系统内置的安全默认值，任何一项都不允许配置为"无限制"。

---

### Edge Cases

- 沙箱工具对应的外部命令本身不存在或无法启动（如路径错误、无执行权限）时，
  这次调用被识别为一种沙箱层面的失败（启动失败），而非"超时"或"非零退出码"，
  但同样通过 Tool Protocol 的既有机制反馈给调用方。
- 子进程产生的标准输出内容超出合理长度时（如工具异常打印了海量数据），
  系统应有截断或类似的保护措施，避免单次工具调用的返回值无限增长。
- 子进程尝试访问其受限工作目录之外的文件路径时，按操作系统的正常文件权限/
  路径限制处理（尽力而为的隔离，不承诺能拦截所有可能的逃逸手段）。
- 同一工具被并发调用多次时，各次调用各自独立的子进程与资源限制，互不干扰、
  互不共享工作目录内容。
- 沙箱工具的资源限制能力在不同操作系统上可能不完全一致（如某些资源限制
  手段仅在特定平台可用）；至少超时这一项能力必须在所有支持的平台上生效。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 工具注册中心 MUST 支持按名称注册工具、按名称查找工具、列出
  全部已注册工具三个操作。
- **FR-002**: 注册同名工具 MUST 被拒绝（返回明确的错误，不静默覆盖或忽略），
  原有的同名工具 MUST 保持不变。
- **FR-003**: 查找不存在的工具名称 MUST 返回明确的"未找到"结果，MUST NOT
  抛出未分类异常。
- **FR-004**: 注册中心 MUST 能同时管理"进程内可信实现"与"沙箱插件"两类工具，
  二者均满足同一个 Tool Protocol，注册中心的查找/列出操作 MUST NOT 区分
  这两类工具的处理方式。
- **FR-005**: MUST 提供一种沙箱工具实现（SandboxedTool），其 invoke() 在
  调用时于隔离的子进程中执行一个预先配置的外部命令，将调用方传入的
  arguments 传递给该子进程，并将其标准输出作为调用结果返回。
- **FR-006**: 沙箱执行 MUST 设置显式的最长执行时间；超过该时间时，子进程
  MUST 被强制终止，MUST NOT 无限期挂起；该项能力 MUST 在所有支持的运行
  平台上生效。
- **FR-007**: 沙箱执行 MUST 对子进程设置资源使用上限（至少包含 CPU 时间与
  内存使用两项）；超限时子进程 MUST 被终止并识别为资源超限失败；该项能力
  MAY 因运行平台不同而具备不同程度的实际约束力，但配置接口本身 MUST 存在
  且 MUST NOT 允许配置为"无限制"。
- **FR-008**: 沙箱执行 MUST 将子进程的工作目录限定在一个专用的临时目录内
  （尽力而为的文件系统隔离）。
- **FR-009**: 本 feature 的进程级沙箱 MUST NOT 声称提供网络访问隔离——
  子进程理论上仍可发起网络请求；此局限性 MUST 在文档中明确说明，
  不得让调用方误以为已获得网络隔离保证。
- **FR-010**: 沙箱执行的失败 MUST 至少区分以下几类，且调用方 MUST 能够
  编程区分：超时、资源超限、启动失败（命令不存在/无权限等）、非零退出码
  （工具自身的业务失败）。所有类型 MUST 通过 Tool Protocol 现有的
  invoke() 异常/返回值机制反馈，MUST NOT 需要 002 ReactEngine 侧做
  任何改动即可兼容处理（工具失败转为观察结果的既有机制）。
- **FR-011**: 每次沙箱执行（无论成功、超时、资源超限还是启动失败）MUST
  产生一条可观测记录，包含 tenant_id、工具名称、执行结果类型、实际执行
  耗时；遥测发送失败 MUST NOT 影响工具执行本身的结果（延续 001-004 的
  遥测容错要求）。
- **FR-012**: 工具注册中心与沙箱执行 MUST NOT 依赖任何平台层组件；单元
  测试 MUST 使用简单的本地示例脚本（正常退出/超时/资源超限/非零退出码/
  启动失败等场景），MUST NOT 依赖真实的第三方插件生态。
- **FR-013**: 本 feature MUST NOT 改变 001/002 已冻结的 Tool Protocol
  签名（`name`/`description`/`invoke(arguments, *, tenant_id) -> str`）；
  沙箱是 `invoke()` 背后的执行环境实现，对调用方（如 002 的 ReactEngine）
  透明。

### Key Entities

- **工具注册中心（ToolRegistry）**: 管理一组按名称索引的已注册工具，
  提供注册/查找/列出三个操作。
- **沙箱工具（SandboxedTool）**: 一种 Tool Protocol 的实现，包装一个外部
  命令及其执行配置（超时、资源上限、工作目录）。
- **沙箱执行结果**: 一次沙箱执行的产物——成功时为标准输出内容；失败时为
  类型化的失败信息（超时/资源超限/启动失败/非零退出码），携带诊断信息
  （如退出码、实际耗时）。
- **沙箱执行遥测记录**: 每次沙箱执行产生的观测数据——tenant_id、工具名称、
  结果类型、实际耗时。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在无平台层组件、无真实第三方插件的条件下，工具注册与沙箱
  执行模块的全部单元测试可一次性通过。
- **SC-002**: 100% 的同名工具注册尝试被拒绝，注册中心中同名工具在任意
  时刻只有一个生效版本。
- **SC-003**: 100% 超过配置超时的沙箱执行在超时时间的合理误差范围内
  （如 1.5 倍时间内）被强制终止，不会无限期挂起。
- **SC-004**: 抽查任意一次沙箱执行的可观测记录，可识别出其 tenant_id、
  工具名称与执行结果类型（成功/超时/资源超限/启动失败/非零退出码之一）。
- **SC-005**: 新开发者按后续 plan 阶段产出的验证指南，可在 15 分钟内用
  本地示例脚本跑通一次成功执行、一次超时、一次非零退出码的完整场景。

## Assumptions

- 沙箱隔离级别采用进程级（子进程 + 资源限制），不采用容器级隔离；这是
  一个已确认的架构决策——进程级隔离在部署与依赖上最简单（零额外运行时
  依赖），隔离强度足以防范失控（资源耗尽、挂起），但不足以防范恶意逃逸，
  该权衡对当前阶段可接受，未来如需更强隔离可作为独立的升级 feature。
- 网络访问隔离不在本 feature 范围内（Assumptions 与 FR-009 已明确），
  沙箱工具的外部命令若需要限制网络访问，需等待未来可能的容器级沙箱能力。
- CPU/内存资源限制的具体实现手段（如何在不同操作系统上施加限制）留待
  plan 阶段确定技术方案；不同平台的实际约束力可以不同，但超时这一项
  能力必须在所有平台上生效（FR-006）。
- "工具业务失败"（子进程正常退出但退出码非零，或输出内容表明失败）与
  "沙箱层面失败"（超时/资源超限/启动失败）需要可区分，但具体的类型
  设计（如异常类层级还是返回值编码）留待 plan 阶段确定。
- 本 feature 不涉及工具的动态加载/热更新、不涉及从外部包管理器安装
  第三方插件、不涉及工具市场或版本管理；工具的外部命令路径与执行配置
  由调用方在注册时显式提供。
- 沙箱工具包装的外部命令假定是调用方已经准备好的可执行文件/脚本
  （如一个 Python 脚本路径），本 feature 不负责这些命令本身的编写、
  分发或权限管理。
