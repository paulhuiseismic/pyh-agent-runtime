# Feature Specification: 多租户强化与审计

**Feature Branch**: `010-multitenant-audit`

**Created**: 2026-08-07

**Status**: Draft

**Input**: User description: "010 多租户强化与审计（平台层：租户配置管理能力、用量/成本审计记录与查询，在 007/008/009 已建立的三个入口之上补齐运维与合规能力）"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 每次请求自动生成可追溯的用量/成本审计记录 (Priority: P1)

作为该平台的运维/合规方，我需要无论调用方通过 REST（007）、CLI（008）
还是消息网关（009）哪一个入口发起请求，每一次请求完成后都自动留下一条
包含所属租户、用量、成本、成功或失败状态的审计记录，供后续核算与追溯，
不需要在事后翻查分散的日志。

**Why this priority**: 这是本 feature 的数据基础——没有可靠、统一的审计
记录，查询（US2）与配额强化（US3）都无从谈起。

**Independent Test**: 可通过分别经三个入口各发起一次请求（用 stub
provider 驱动，覆盖成功与失败两种结果），独立验证：每次请求完成后都
产生一条审计记录，字段包含正确的租户标识、用量/成本、结果状态与来源
入口，且审计记录写入失败不会导致原始请求本身失败。

**Acceptance Scenarios**:

1. **Given** 一次通过任意入口发起的请求成功完成，**When** 检查审计
   存储，**Then** 能找到一条对应的记录，包含正确的租户标识、token
   用量、成本、成功状态与来源入口标识。
2. **Given** 一次请求处理过程中内核失败，**When** 检查审计存储，
   **Then** 同样能找到一条对应的记录，标记为失败状态（用量/成本可能
   为零或部分产生）。
3. **Given** 审计记录的写入本身发生异常（如存储暂时不可用），**When**
   该情况发生，**Then** 原始请求的处理结果不受影响，仍按正常流程返回
   给调用方。

---

### User Story 2 - 运维方查询某租户的历史用量与成本汇总 (Priority: P2)

作为该平台的运维/合规方，我需要通过一个查询接口，按租户与时间范围
查看该租户在此期间的请求总数、总用量与总成本，而不需要逐条翻阅原始
审计记录或依赖外部可观测性工具。

**Why this priority**: 这是审计数据"可用"而非仅仅"存在"的关键一步，
依赖 US1 已经产生的审计记录，故排在其后。

**Independent Test**: 可通过先用 US1 的方式产生若干条已知用量/成本的
审计记录，再对同一租户、覆盖这些记录时间戳的时间范围发起查询，独立
验证返回的汇总总数与预期一致；对不存在任何记录的时间范围查询，验证
返回结果为空汇总而不是错误。

**Acceptance Scenarios**:

1. **Given** 某租户在指定时间范围内有若干条审计记录，**When** 该租户
   查询自己在该时间范围内的用量汇总，**Then** 返回的总请求数/总用量/
   总成本与这些记录汇总后的结果一致。
2. **Given** 指定的时间范围内该租户没有任何审计记录，**When** 发起
   查询，**Then** 返回一个全为零的空汇总结果，而不是错误响应。
3. **Given** 调用方提供的身份标识不属于被查询的租户，**When** 发起
   查询，**Then** 请求被拒绝，不返回任何其他租户的用量数据。

---

### User Story 3 - 租户成本配额超限时新请求被拒绝 (Priority: P3)

作为该平台的运维方，我需要为特定租户配置一个时间窗口内的成本上限，
当该租户在当前窗口内的累计成本达到上限时，其后续新请求被拒绝，避免
单个租户的失控调用造成超出预期的成本支出。

**Why this priority**: 这是在 US1 已有审计数据基础上新增的一层保护
能力，技术上依赖 US1 产生的用量数据作为判断依据，属于锦上添花的强化
项，故排在最后。

**Independent Test**: 可通过为某租户配置一个很小的成本配额，先用
stub provider 驱动若干次请求使其累计成本达到该配额，再发起下一次
请求，独立验证：该请求被明确拒绝，且未配置配额的其他租户不受影响。

**Acceptance Scenarios**:

1. **Given** 某租户配置了一个时间窗口内的成本配额，且当前窗口内累计
   成本已达到该配额，**When** 该租户发起新请求，**Then** 请求在触发
   任何内核调用之前即被拒绝，返回明确的"配额超限"响应。
2. **Given** 某租户未配置任何成本配额，**When** 该租户发起请求，
   **Then** 请求不受本 feature 新增的配额检查影响（沿用 007/008/009
   已有的行为）。
3. **Given** 时间窗口已过期（如进入新的一天），**When** 该租户在新
   窗口内发起请求，**Then** 配额判断基于新窗口内的累计成本重新计算，
   不受上一窗口用量影响。

---

### Edge Cases

- 审计记录的写入本身失败时，系统 MUST NOT 让原始请求因此失败——
  审计是最佳努力的旁路记录，不是请求处理路径的强依赖（US1 验收
  场景 3）。
- 查询一个没有任何审计记录落在其内的时间范围时，MUST 返回全零的
  空汇总结果，而不是报错（US2 验收场景 2）。
- 配额检查所依据的"当前窗口累计成本"MUST 与查询接口报告的汇总数据
  来自同一份审计记录，不引入第二套独立记账机制，避免两者口径不一致。
- 同一租户在配额边界附近并发发起多个请求时，配额判断 MUST 避免明显
  的超额放行（多个并发请求同时通过检查、导致总成本显著超出配额）。
- 一个租户从平台配置中被移除后，其此前已产生的历史审计记录 MUST
  保留可查询，不因租户配置变更而被清除或失效。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 为每一次通过 REST（007）、CLI（008）或消息
  网关（009）任一入口完成的请求生成一条审计记录，记录内容至少包含：
  所属租户标识、来源入口、发生时间、token 用量、成本、处理结果
  （成功/失败）。
- **FR-002**: 审计记录 MUST 持久化存储，在进程重启后仍可被查询到。
- **FR-003**: 审计记录的写入 MUST 为最佳努力操作——写入失败 MUST NOT
  导致原始请求的处理结果受到影响（呼应 Edge Cases，与 007 长期记忆
  提炼失败不影响主流程的既有设计原则一致）。
- **FR-004**: 系统 MUST 提供一个查询能力，按租户标识与时间范围返回
  该租户在此期间的请求总数、总 token 用量、总成本的汇总结果。
- **FR-005**: 查询能力 MUST 只允许调用方查询其自身所属租户的用量
  数据；调用方身份与被查询租户不匹配的请求 MUST 被拒绝。
- **FR-006**: 系统 MUST 支持为特定租户配置一个时间窗口内的成本配额；
  未配置配额的租户 MUST NOT 受本 feature 新增的配额检查影响。
- **FR-007**: 当某租户在当前配额时间窗口内的累计成本达到其配置的
  配额上限时，该租户的新请求 MUST 在触发任何内核调用之前被拒绝，
  返回明确可区分的"配额超限"响应。
- **FR-008**: 配额检查所依据的累计成本 MUST 直接来自 FR-001 产生的
  审计记录，MUST NOT 引入第二套独立的用量统计机制（避免口径不一致，
  呼应最简实现原则）。
- **FR-009**: 系统 MUST 在配额时间窗口过期后，基于新窗口内的累计
  成本重新判断，不受上一窗口用量影响。

### Key Entities *(include if feature involves data)*

- **审计记录**：一次已完成请求的用量/成本快照，包含租户标识、来源
  入口（REST/CLI/消息网关）、发生时间、token 用量、成本、处理结果
  （成功/失败）、可选的会话/消息关联标识。
- **租户成本配额（可选配置）**：为特定租户配置的时间窗口内成本上限，
  未配置时该租户不受此限制。
- **用量查询结果**：按租户与时间范围聚合后的汇总——请求总数、总
  token 用量、总成本。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% 通过任一入口（REST/CLI/消息网关）完成的请求，
  无论成功或失败，都产生一条对应的审计记录。
- **SC-002**: 运维方可以在不查看原始日志或依赖外部可观测性工具的
  情况下，通过一次查询获得某租户在任意指定时间范围内的用量/成本
  汇总。
- **SC-003**: 审计记录在进程重启后依然可被完整查询到，不因进程
  生命周期结束而丢失。
- **SC-004**: 审计记录写入失败的情形下，100% 的原始请求仍然正常
  返回处理结果，不受审计写入失败影响。
- **SC-005**: 100% 达到其配置成本配额的租户，后续请求在触及任何
  内核资源之前即被拒绝，直至配额窗口重置。
- **SC-006**: 100% 未配置成本配额的租户，其请求处理行为与本 feature
  上线前完全一致。
- **SC-007**: 配额判断所用的累计成本与查询接口报告的汇总数据 100%
  来自同一份审计数据，两者不会出现口径不一致的情形。

## Assumptions

- 用量/成本审计记录采用本地持久化存储（与 003 会话记忆同风格的
  技术选型交由 plan 阶段决定），并新增一个查询能力；不依赖必须先
  部署外部可观测性工具（如 Langfuse）才能回答"某租户花了多少钱"
  这一基本问题——这是运维在合规场景下的最低可用保障，外部工具
  （OTel/Langfuse）仍然是更丰富分析能力的补充，二者不互斥。
- 查询能力默认只允许租户查询自己的用量数据（FR-005），不引入
  "运维管理员可查询任意租户"这一更高权限层级——v1 沿用 007-009 已
  建立的"调用方身份与其自身租户一一对应"的安全模型，不新增权限体系；
  若未来需要跨租户查询能力，留给未来按需扩展。
- 租户成本配额为可选配置项（FR-006），未配置的租户不受影响——本
  feature 新增的是在 001 已有的"单次调用 token/成本上限"（宪法原则
  IV）之上的第二层保护（"一段时间窗口内的累计成本上限"），二者互不
  替代：单次调用上限任何时候都生效，累计配额是额外的、可选的强化项。
- 租户配置（含新增的配额字段）仍采用静态配置文件的方式声明，与
  007-009 一致；不引入运行时动态增删改查租户配置的管理 API，相关
  能力留给未来按需评估。
- 配额时间窗口固定为按自然日计算（如 UTC 每日 0 点重置），不支持
  滚动窗口或自定义窗口长度——v1 选择最简单、最容易理解的窗口语义，
  更灵活的窗口配置留给未来按需扩展。
- 本 feature 只覆盖"记录 → 查询 → （可选）配额强化"这一最小闭环；
  更复杂的审计报表、多维度分析、导出能力留给未来按需评估。
