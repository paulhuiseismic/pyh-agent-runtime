# Feature Specification: 长期记忆

**Feature Branch**: `004-long-term-memory`

**Created**: 2026-07-26

**Status**: Draft

**Input**: User description: "长期记忆：实现内核的跨会话长期记忆能力，作为 memory 子模块的独立扩展，
与 003 已交付的会话级 SqliteMemory（按 session_id 隔离、自动压缩）区分开——长期记忆存储的是
'事实/偏好'这类不随单次对话结束而失效的信息，生命周期独立于任何单个会话。核心能力：按 tenant_id
隔离存储一组记忆条目；支持从一次会话历史中提炼记忆条目（显式触发，经一次 provider LLM 调用）；
支持查询与当前上下文相关的记忆条目（本 feature 采用最简实现：按最近写入时间排序、数量上限可配置，
不引入向量检索，但接口设计不阻碍未来替换）；新条目与已有条目冲突/重复时需要合理的处理策略（可以是
简单的同类覆盖）；提炼与查询均可独立单元测试、不依赖平台层、提炼调用继承 provider 限额与 span、
操作本身也需产生可观测记录；默认持久化复用 003 的 SQLite 方案，独立新表，不与会话消息耦合。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 从一次对话中提炼长期记忆 (Priority: P1)

作为内核的上层调用方，在一次对话结束时，我可以把这次对话的历史交给长期记忆模块，
它会提炼出其中值得长期记住的偏好或事实，并存入该租户的长期记忆库，供未来的对话使用。

**Why this priority**: 这是长期记忆存在的入口——没有提炼能力，记忆库永远是空的，
后续的查询与冲突处理都无从谈起。

**Independent Test**: 用 stub provider 返回预设的提炼结果，传入一段对话历史调用提炼操作，
验证提炼出的记忆条目被正确写入指定租户的存储，全程不需要真实模型或平台层组件。

**Acceptance Scenarios**:

1. **Given** 一段包含明确偏好陈述的对话历史（如"我更喜欢简洁的回答"）, **When** 对该租户
   触发一次提炼, **Then** 提炼出的记忆条目被写入该租户的长期记忆库。
2. **Given** 一段不包含任何值得记住信息的对话历史, **When** 触发提炼,
   **Then** 提炼操作正常完成，不强行写入无意义的记忆条目（提炼结果为空时不写入）。
3. **Given** 提炼所需的 LLM 调用本身失败（超时/超限等 provider 已定义的类型化异常）,
   **When** 触发提炼, **Then** 提炼操作以该异常终止，长期记忆库不受影响
   （不写入部分或损坏的数据）。

---

### User Story 2 - 查询与当前对话相关的长期记忆 (Priority: P2)

作为调用方，在开始一次新对话前，我可以查询该租户已有的长期记忆条目，
将其注入到新对话的上下文中，使 agent 的回应能体现出对该租户历史偏好的了解。

**Why this priority**: 查询是长期记忆产生实际价值的出口，但依赖 User Story 1
已经写入了数据，故列为第二优先级。

**Independent Test**: 预先写入若干条记忆条目，调用查询操作，验证返回的条目集合
符合"按最近写入时间排序、数量不超过配置上限"的规则；验证不同租户的查询互不可见。

**Acceptance Scenarios**:

1. **Given** 某租户已有若干条长期记忆, **When** 查询该租户的相关记忆,
   **Then** 返回的条目集合数量不超过配置上限，按最近写入时间排序（最新的在前）。
2. **Given** 某租户尚无任何长期记忆, **When** 查询该租户的相关记忆,
   **Then** 返回空列表，不报错。
3. **Given** 两个不同租户各自写入了记忆条目, **When** 分别查询各自的记忆,
   **Then** 各自只能看到自己租户的条目，看不到对方的数据。

---

### User Story 3 - 新记忆与已有记忆冲突时的处理 (Priority: P3)

作为长期记忆库的维护者（系统本身），当新提炼出的记忆条目与已有条目属于同一类信息的更新时
（比如用户此前说喜欢简洁回答，这次说喜欢详细回答），系统应有合理策略避免库中同时存有
自相矛盾的记忆，也避免记忆库因反复提炼同类信息而无限增长。

**Why this priority**: 这是长期记忆保持"有效可用"而非"越用越乱"的关键保障，
但依赖前两个故事已经建立的写入与查询能力，故列为第三优先级。

**Independent Test**: 连续两次提炼产生同一类别的记忆条目（如同为"回答风格偏好"），
验证第二次写入后库中该类别只保留一条（新的覆盖旧的），而非无限累加。

**Acceptance Scenarios**:

1. **Given** 长期记忆库中已存在一条"回答风格偏好"类别的记忆, **When** 新的提炼
   产生了同类别的新记忆, **Then** 新记忆覆盖旧记忆，库中该类别仅保留一条。
2. **Given** 长期记忆库中已存在多个不同类别的记忆, **When** 新提炼产生了一个
   全新类别的记忆, **Then** 新记忆作为独立条目新增，不影响其他类别的已有记忆。
3. **Given** 反复对同一租户执行提炼（如每次对话结束都提炼一次）, **When** 检查
   该租户的记忆条目总量, **Then** 条目总量不随提炼次数无限增长（同类覆盖生效）。

---

### Edge Cases

- 提炼时会话历史为空或过短（无实质内容）时，提炼操作正常完成且不写入任何记忆条目
  （视为"无值得记住的内容"，与 US1 场景 2 一致）。
- 查询时配置的数量上限为 0 或负数时，请求在查询开始前被拒绝（呼应宪法"任何限额
  不允许无限制"，此处体现为上限必须是正数）。
- 同一租户并发触发多次提炼时，各自写入的记忆条目不丢失、不相互覆盖对方正常的
  新增（除非确实属于同一类别的合理覆盖场景）。
- 记忆条目的"类别"判定依赖提炼步骤本身的输出，若提炼结果未能给出可用的类别信息，
  按"无法判定类别"处理为始终新增（不与任何已有条目比较覆盖），避免误覆盖。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 长期记忆模块 MUST 按 `tenant_id` 隔离存储记忆条目集合；不同
  `tenant_id` 之间的记忆条目 MUST 完全隔离，任一方 MUST NOT 能读取另一方的数据。
- **FR-002**: 记忆条目 MUST NOT 与任何特定 `session_id` 绑定，其生命周期
  MUST 独立于任何单个会话（不随会话压缩或结束而失效）。
- **FR-003**: 长期记忆模块 MUST 提供显式触发的提炼操作：接收一段会话历史
  （Message 列表）与 `tenant_id`，通过一次 provider LLM 调用提炼记忆条目并写入
  该租户的存储；提炼 MUST NOT 像 003 的压缩那样自动触发。
- **FR-004**: 提炼结果为空（无值得记住的内容）时，提炼操作 MUST 正常完成且
  MUST NOT 写入无意义的记忆条目。
- **FR-005**: 提炼所需的 LLM 调用失败时（provider 抛出的类型化异常），提炼操作
  MUST 以该异常终止，MUST NOT 写入部分或损坏的记忆数据。
- **FR-006**: 长期记忆模块 MUST 提供查询操作：接收 `tenant_id` 与一个可配置的
  数量上限，返回该租户的记忆条目列表，按最近写入时间排序（最新在前）；数量上限
  MUST 为正整数，非正数 MUST 在查询开始前被拒绝。
- **FR-007**: 查询接口的设计 MUST NOT 阻碍未来替换为基于语义相似度的检索实现
  （即当前"按时间排序"只是本 feature 的具体实现策略，接口本身不假设排序方式）。
- **FR-008**: 新记忆条目写入时，若与已有条目判定为同一类别，MUST 用新条目
  覆盖旧条目（同类别仅保留一条）；MUST NOT 因反复提炼同类信息导致条目无限增长；
  无法判定类别的条目 MUST 作为独立新条目写入，MUST NOT 被错误覆盖。
- **FR-009**: 提炼与查询操作 MUST NOT 依赖任何平台层组件；单元测试 MUST 使用
  stub provider 与真实本地存储，MUST NOT 依赖真实模型服务。
- **FR-010**: 提炼发起的 LLM 调用 MUST 通过 provider 完成，因而自动获得
  provider 已有的超时、token/成本上限与 GenAI span（继承自 001，不重复实现）。
- **FR-011**: 每次提炼与查询操作 MUST 产生可关联到 `tenant_id` 与操作类型
  （提炼/查询）的遥测记录；遥测发送失败 MUST NOT 影响操作本身的执行与结果
  （延续 001/002/003 的遥测容错要求）。
- **FR-012**: 默认持久化实现 MUST 复用 003 已建立的 SQLite（WAL）方案，
  使用一张独立于会话消息表的新表；长期记忆的存储与查询逻辑 MUST NOT 与
  003 的会话消息存储、自动压缩逻辑耦合。

### Key Entities

- **记忆条目（MemoryEntry）**: 一条长期记忆——所属租户、内容文本、类别（可能为
  "无法判定"）、写入时间；不含 `session_id`。
- **提炼请求**: 一次提炼操作的输入——待提炼的会话历史（Message 列表）、
  目标租户标识。
- **提炼结果**: 一次提炼产生的记忆条目集合（可能为空）。
- **查询请求**: 一次查询操作的输入——目标租户标识、返回数量上限。
- **冲突处理策略**: 新条目与已有条目按类别比较，同类别覆盖、无法判定类别
  的条目独立新增。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在无平台层组件、无真实模型服务的条件下，长期记忆模块全部单元
  测试可一次性通过。
- **SC-002**: 100% 的跨租户查询尝试均被隔离——任一租户无法读取到其他租户的
  记忆条目。
- **SC-003**: 反复对同一租户、同一类别信息触发提炼 N 次后，该类别在记忆库中
  始终只保留 1 条（不随 N 增长）。
- **SC-004**: 抽查任意一次提炼或查询操作的遥测记录，可识别出其 `tenant_id`
  与操作类型。
- **SC-005**: 提炼失败（LLM 调用异常）后，长期记忆库中不出现部分写入或
  损坏的记忆条目——库状态与提炼发起前完全一致。

## Assumptions

- 提炼时如何从对话历史中判断"哪些信息值得记住"以及如何为记忆条目分配"类别"，
  具体提示词与判定逻辑留待 plan 阶段确定技术实现；本 spec 只约束行为契约：
  一次提炼产生零或多条带类别标注（或标注为"无法判定"）的记忆条目。
- 查询的"相关性"在本 feature 中简化为"按时间新近程度排序 + 数量上限"，
  不做与查询上下文的语义匹配；调用方若需要更精细的相关性排序，需等待未来
  引入语义检索能力的 feature。
- 数量上限、类别判定等的具体默认值留待 plan 阶段确定，但均 MUST 有安全默认值。
- 本 feature 不支持记忆条目的手动删除/编辑；这类管理操作留给未来可能的平台层
  能力，不在本次范围。
- 长期记忆与 003 会话记忆是内核 memory 子模块下的两个独立能力，二者可以共存
  于同一 SQLite 数据库文件（不同表），但各自的读写逻辑互不调用对方的压缩/
  覆盖机制。
