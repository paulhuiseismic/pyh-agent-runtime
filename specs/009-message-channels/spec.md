# Feature Specification: message 多渠道收发（消息网关）

**Feature Branch**: `009-message-channels`

**Created**: 2026-08-07

**Status**: Draft

**Input**: User description: "009 message 多渠道收发（平台层新增消息网关，支持多个外部渠道接入/发送适配，复用同一套 AgentService 处理路径）"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 外部渠道发来一条消息并异步收到回复 (Priority: P1)

作为接入该 runtime 的外部消息渠道（如某个 IM 平台的 webhook 转发方），
我把用户在该渠道发的一条消息投递给这个 runtime 的消息网关，网关立即
确认收到，随后在后台完成一次 agent 调用，处理完成后主动把回复投递回
该渠道配置好的接收地址，我无需长时间保持连接等待处理完成。

**Why this priority**: 这是本 feature 的核心价值——把已有的 007/008
调用路径（`AgentService`）第一次接入"消息"这一异步交互形态，是消息网关
存在的根本原因。

**Independent Test**: 可通过向网关的接入端点投递一条携带合法渠道标识、
外部消息 ID、发送者与文本内容的消息，独立验证：网关立即返回确认（不
等待处理完成）；随后（用 stub provider 驱动）网关主动调用该渠道配置的
出站接收地址，投递内容包含处理结果与可与原消息关联的标识。

**Acceptance Scenarios**:

1. **Given** 已配置一个渠道实例（渠道标识、所属租户、出站回调地址），
   **When** 向该渠道投递一条合法消息，**Then** 网关立即返回确认响应
   （不等待 agent 处理完成），且响应时间不受 agent 处理耗时影响。
2. **Given** 一条消息已被接收确认，**When** 后台完成 agent 处理，
   **Then** 网关调用该渠道配置的出站回调地址，投递的内容包含最终结果
   文本，且携带可关联回原始消息的标识（外部消息 ID 或等价标识）。
3. **Given** 后台处理该消息时内核任一环节失败，**When** 处理结束，
   **Then** 网关同样调用出站回调地址，但投递内容明确标识为失败结果，
   而不是静默丢弃或长时间无任何反馈。

---

### User Story 2 - 未配置的渠道请求在触发任何处理前被拒绝 (Priority: P2)

作为该平台的运维方，我需要网关对来自未配置渠道标识的投递请求立即拒绝，
不进入任何后续处理，避免未授权的调用方冒充某个渠道消耗内核资源。

**Why this priority**: 这是多租户环境下的基本安全边界，呼应 007/008
已建立的"未识别身份前不触及内核"原则，但依赖 US1 建立的接入路径才能
验证，故排在其后。

**Independent Test**: 可通过向网关投递一条携带未配置渠道标识的消息，
独立验证：请求立即被拒绝，且不触发任何后台处理、不产生任何出站回调
调用。

**Acceptance Scenarios**:

1. **Given** 一条消息携带的渠道标识未在平台配置中出现，**When** 投递
   该消息，**Then** 网关立即返回明确的"渠道未识别"拒绝响应，不触发
   任何后台处理或出站回调。
2. **Given** 同一条外部消息因渠道方重试机制被重复投递两次（相同渠道
   标识 + 相同外部消息 ID），**When** 第二次投递到达，**Then** 网关
   识别为重复消息，不二次触发 agent 处理、不产生第二次出站回调，
   避免重复回复同一条外部消息。

---

### User Story 3 - 消息处理与 007/008 保持一致的可观测性与会话延续 (Priority: P3)

作为该平台的运维/合规方，我需要每一条消息触发的内核可观测记录都携带
一致的租户标识，且同一会话/对话串的多条消息之间能够延续此前积累的
上下文，与 REST（007）/CLI（008）入口的行为保持一致。

**Why this priority**: 这是合规与用户体验一致性的收尾要求，技术上
复用 007/008 已有机制，依赖 US1 建立的处理路径才能验证，故排在最后。

**Independent Test**: 可通过连续投递两条携带相同渠道标识与相同"对话
标识"的消息，独立验证第二条消息的处理结果体现第一条消息积累的上下文；
检查一次成功处理触发的全部内核可观测记录，验证均携带一致的租户标识。

**Acceptance Scenarios**:

1. **Given** 两条消息共享同一渠道标识与同一对话标识，**When** 依次
   投递这两条消息，**Then** 第二条消息的处理结果体现第一条消息已经
   积累的会话上下文（复用 003 会话记忆）。
2. **Given** 一条消息触发了成功的 agent 处理，**When** 检查该次处理
   产生的全部内核可观测记录，**Then** 这些记录 100% 携带与该消息所属
   渠道对应的租户标识一致。

---

### Edge Cases

- 出站回调地址不可达或返回失败状态时，系统 MUST 按一个显式的、有限的
  次数重试，MUST NOT 无限重试或无限期挂起（呼应宪法原则 IV）；达到重试
  上限后仍失败的，MUST 记录为明确的"回调投递失败"结果，不得静默丢弃。
- 同一渠道标识 + 同一外部消息 ID 的重复投递（渠道方常见的"至少一次"
  投递语义）MUST 被识别为重复，不重复触发内核处理（见 US2 验收场景 2）。
- 消息未携带对话/会话标识时，MUST 视为一次全新的、无历史上下文的独立
  调用（与 007/008 未提供 `session_id` 时的语义一致）。
- 消息体缺少必填字段（如渠道标识、外部消息 ID、文本内容）时，MUST 在
  触发任何后台处理前即返回明确的参数校验失败响应。
- 单次后台 agent 处理耗时超出配置的最长等待时间时，MUST 终止等待并把
  超时作为明确的失败结果通过出站回调投递（呼应 007/008 FR-009 的超时
  约束，延伸到异步处理场景）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 提供一个渠道无关的消息接入端点，接收「渠道
  标识、外部消息 ID、发送者标识、文本内容、可选的对话/会话标识」，
  并在触发任何 agent 处理之前立即返回确认响应，不等待处理完成。
- **FR-002**: 系统 MUST 通过静态配置的「渠道标识 → 租户标识 + 出站
  回调地址」映射表识别一条消息所属的渠道与租户；引用未配置渠道标识的
  请求 MUST 在触发任何后台处理之前被拒绝。
- **FR-003**: 系统 MUST 将已接受的消息路由到与 007（REST）/008（CLI）
  完全相同的内部统一处理路径（`AgentService`），MUST NOT 为消息网关
  重新实现租户识别、内核调用组合等已由 007 建立的逻辑。
- **FR-004**: 系统 MUST 异步完成每条已接受消息的处理，处理完成（无论
  成功或失败）后，MUST 主动调用该消息所属渠道配置的出站回调地址，
  投递内容 MUST 包含处理结果，并携带可关联回原始消息的标识（外部
  消息 ID 或等价标识）。
- **FR-005**: 系统 MUST 支持会话延续——共享同一渠道标识与同一对话/
  会话标识的多条消息复用该会话此前积累的历史上下文（复用 003 会话
  记忆能力，与 007/008 的 `session_id` 语义一致）；未提供对话/会话
  标识的消息 MUST 视为全新的、无历史上下文的独立调用。
- **FR-006**: 系统 MUST 识别同一渠道标识 + 同一外部消息 ID 的重复
  投递，重复投递 MUST NOT 触发第二次 agent 处理或第二次出站回调
  调用。
- **FR-007**: 系统 MUST 为以下情形提供彼此可区分的结果反馈：渠道未
  识别（同步拒绝响应）、消息参数校验失败（同步拒绝响应）、内核处理
  失败（异步出站回调）、处理超时（异步出站回调）、成功（异步出站
  回调）。
- **FR-008**: 系统 MUST 对出站回调这一外部调用设置显式超时（呼应
  宪法原则 IV）；调用失败（超时或错误响应）MUST 按一个显式的、有限
  的次数重试，MUST NOT 无限重试。
- **FR-009**: 系统 MUST 对每条消息触发的每一次内核调用（LLM 调用、
  工具执行等）传递识别出的租户标识，使这些调用产生的可观测记录都
  携带一致的租户标识（呼应宪法原则 V，与 007/008 FR-006 语义一致）。
- **FR-010**: 系统 MUST 对单条消息的后台处理设置一个显式的最长等待
  时间；超过该时间 MUST 终止处理，并将超时作为明确的失败结果通过
  出站回调投递（呼应 007/008 FR-009 的超时约束）。

### Key Entities *(include if feature involves data)*

- **渠道实例配置**：一个可投递消息的渠道接入点，包含渠道标识、所属
  租户标识、出站回调地址、出站回调所需的可选凭据。
- **入站消息**：一次外部投递的载荷，包含渠道标识、外部消息 ID、发送者
  标识、文本内容、可选的对话/会话标识。
- **出站回复**：一次处理完成后投递给渠道出站回调地址的载荷，包含处理
  结果（成功/各类失败）、最终结果文本或失败原因、可关联回原始消息的
  标识。
- **已处理消息记录**：用于识别重复投递的最小状态——已处理过的
  「渠道标识 + 外部消息 ID」组合。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 外部渠道投递一条消息后，无论 agent 实际处理耗时多久，
  都能在恒定的短时间内收到接入确认，不被处理耗时阻塞。
- **SC-002**: 100% 来自未配置渠道标识的投递请求，在触及任何内核资源
  之前即被拒绝。
- **SC-003**: 100% 的重复投递（相同渠道标识 + 相同外部消息 ID）不会
  产生第二次 agent 处理或第二次回复投递。
- **SC-004**: 每一条被接受的消息，无论处理成功或失败，系统都 MUST
  尝试通过出站回调投递明确、可区分的结果反馈；回调地址本身不可达时，
  系统在达到重试上限后 MUST 如实记录投递失败（而非静默丢弃），而不是
  从一开始就放弃尝试（`/speckit-analyze` F2 修正——原表述"不存在投递
  后石沉大海的情形"过度承诺：若渠道方的回调地址本身长期不可达，外部
  确实可能收不到任何反馈，系统能保证的是"已尝试且失败被如实记录"，
  而非"外部必然收到反馈"）。
- **SC-005**: 共享同一对话标识的多条消息，100% 能够看到此前消息积累
  的上下文，与消息来自哪个渠道无关。
- **SC-006**: 每一条消息触发的内核可观测记录，100% 携带与该消息所属
  租户一致的标识。
- **SC-007**: 消息网关的租户识别、内核调用组合逻辑与 007/008 共享
  同一套实现——衡量方式为：新增消息网关未修改或复制 007 已有的
  `AgentService`/租户识别相关实现代码。

## Assumptions

- v1 只交付一个渠道无关的通用 Webhook 接入/出站回调抽象，不绑定任何
  具体渠道厂商（如 Slack、企业微信、邮件等）的私有 API 或签名校验
  机制；未来接入具体渠道厂商时，作为独立的适配器按需扩展，不在本
  feature 范围内实现。
- 消息处理采用异步回调模型（FR-004）：接入请求立即确认、处理完成后
  主动回调，而非保持连接同步等待——这与多数真实 IM/webhook 平台的
  短超时限制相符，也是与 007（REST）/008（CLI）的同步阻塞模型的
  唯一交互模式差异。
- 渠道标识到租户的映射采用静态配置（FR-002），与 007 静态 API Key→
  租户映射的设计风格一致，不引入动态渠道注册机制。
- 出站回调失败时的重试为有限次数的进程内重试（FR-008），不引入消息
  队列/持久化重试基础设施；如遇进程崩溃，尚未完成重试的失败回调会
  丢失——v1 接受这一权衡，更强的可靠性保障留给未来按需评估。
- 重复投递识别（FR-006）采用进程内存状态，不追求跨进程/多实例部署下
  的强一致性去重——与 007/008 已有的"不追求跨进程强一致性"假设一致。
- 本 feature 只覆盖"接入消息 → 异步处理 → 出站回调"这一最小闭环；
  渠道配置的管理界面、消息内容审计报表等能力留给未来 feature（010
  多租户强化与审计）。
